# W09 — Sincronização de marcações offline

A API recebe marcações sem modificar sua hora original e confirma cada item
somente depois do commit no PostgreSQL. As rotas ficam no Blueprint mobile;
validação, autorização, geofencing e persistência ficam em `app/services/`.

## Atualizar o ambiente

Na raiz do repositório, com a conexão PostgreSQL configurada no `.env`:

```powershell
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m flask --app app:create_app db upgrade
.\.venv\Scripts\python.exe run.py
```

A migration `0002` (`0002_w09_marcacoes_offline.py`) acrescenta dispositivos, selfies, políticas de localização
e evidências de sincronização. Preserva as marcações anteriores e os bloqueios de
UPDATE/DELETE/TRUNCATE. As novas tabelas também têm RLS sem acesso público.
O downgrade é bloqueado se já existirem dispositivos, selfies ou marcações W09,
para evitar a perda dessas evidências. Os testes usam apenas PostgreSQL local;
a alteração do Supabase online acontece quando você executar `db upgrade`.

## Autenticação e aparelho cadastrado

Os dois endpoints exigem `Authorization: Bearer TOKEN_FLASK`. O JWT assinado
deve conter `sub` com o UUID do funcionário e as claims `empresa_id` e
`dispositivo_id`. O Service confirma no banco que a empresa e o funcionário
estão ativos e que o papel é `Funcionario`. Não aceita o perfil enviado no body.

O aparelho deve estar cadastrado em `Dispositivos`, ativo e vinculado à mesma
empresa e ao mesmo funcionário. Seu ID também deve coincidir com a claim do JWT.
Um ID desconhecido, inativo ou incompatível produz uma marcação **Recusada**;
o UUID informado pelo aparelho permanece registrado como evidência.

O login real está implementado em `/api/mobile/auth/login`: envie `email`,
`senha` e `dispositivo_id` para obter o token vinculado ao aparelho cadastrado.
O cadastro HTTP de aparelhos será integrado em uma etapa própria.
Não há cadastro automático pelo lote. Os tokens fictícios do painel Flutter
não autenticam esta API. Para testar agora, um operador do backend pode usar
`flask shell`, depois de cadastrar uma empresa, um usuário `Funcionario` e sua
alocação válidos:

```powershell
.\.venv\Scripts\python.exe -m flask --app app:create_app shell
```

```python
from uuid import UUID
from flask_jwt_extended import create_access_token
from app import db
from app.models import Dispositivos

empresa_id = UUID("UUID_REAL_DA_EMPRESA")
usuario_id = UUID("UUID_REAL_DO_FUNCIONARIO")
aparelho = Dispositivos(
    empresa_id=empresa_id, usuario_id=usuario_id, nome="Celular de teste"
)
db.session.add(aparelho)
db.session.commit()
token = create_access_token(
    identity=str(usuario_id),
    additional_claims={
        "empresa_id": str(empresa_id), "dispositivo_id": str(aparelho.id)
    },
)
print(aparelho.id)
print(token)
```

Substitua os placeholders pelos UUIDs reais. Essa operação é feita no console
confiável do servidor, sem criar uma rota pública de emissão de tokens.

## Enviar um lote

`POST /api/mobile/marcacoes/lote`, com `Content-Type: application/json`:

```json
{
  "marcacoes": [
    {
      "evento_cliente_id": "f3a06375-02eb-4d08-81d2-ff06f1b3039a",
      "dispositivo_id": "aaaaaaaa-aaaa-4aaa-8aaa-aaaaaaaaaaaa",
      "alocacao_id": "bbbbbbbb-bbbb-4bbb-8bbb-bbbbbbbbbbbb",
      "tipo": "Entrada",
      "ocorrido_em": "2026-10-05T08:00:00-03:00",
      "desvio_relogio_segundos": -15,
      "registrado_offline": true,
      "posicao": {
        "latitude": -8.0,
        "longitude": -35.0,
        "precisao_metros": 5
      }
    }
  ]
}
```

Também é aceito um array diretamente no body. Troque os UUIDs do dispositivo e
da alocação pelos IDs reais. `evento_cliente_id` é gerado no celular antes de
guardar a marcação na fila; deve permanecer igual em todas as retransmissões.

| Campo | Contrato |
| --- | --- |
| `evento_cliente_id` | UUID da marcação, obrigatório |
| `dispositivo_id` | UUID do aparelho, obrigatório |
| `alocacao_id` | UUID da alocação do funcionário autenticado, obrigatório |
| `tipo` | `Entrada`, `Saida`, `InicioIntervalo` ou `FimIntervalo` |
| `ocorrido_em` | ISO 8601 com timezone explícito, obrigatório |
| `desvio_relogio_segundos` | Inteiro com sinal, em segundos, obrigatório |
| `registrado_offline` | Booleano, obrigatório |
| `posicao` | Objeto com latitude/longitude e precisão opcional; pode ser omitido ou `null` |

O desvio é evidência do relógio do aparelho e não é o offset do fuso horário.
O backend não corrige `ocorrido_em` nem estima desvio pela demora do envio:
um lote offline pode chegar muito depois da marcação. Guarda o payload original,
o offset em minutos, o desvio e o indicador offline. O PostgreSQL preenche
`recebido_em` na inserção. Os timestamps retornados são normalizados para UTC.

Distância, situação, motivos, empresa, funcionário e hora de recebimento não
são aceitos como campos do aplicativo. Campos desconhecidos, coordenadas
inválidas e timestamps sem timezone retornam erro de validação por item.
O limite padrão é de 500 marcações por lote e 5 MiB por requisição.

## Classificação no servidor

O `GeofencingService` calcula a distância por Haversine a partir das coordenadas
e do centro do setor. A marcação guarda um snapshot do centro, raio, política e
limite de desvio usados na decisão; alterações futuras no setor não mudam isso.

`Setores.politica_localizacao` é um adaptador compatível com W09. Os campos
persistidos são `acao_fora_perimetro` e `ignorar_localizacao`, com estas opções:

| Política | Dentro do perímetro | Fora do perímetro ou sem posição |
| --- | --- | --- |
| `Bloquear` (padrão) | Aceita, se o desvio for pequeno | Recusada |
| `Pendente` | Aceita, se o desvio for pequeno | Pendente de análise |
| `Ignorar` | Aceita, se o desvio for pequeno | Aceita, se o desvio for pequeno |

O limite padrão de `limite_desvio_relogio_segundos` é 120 segundos. A comparação
usa o valor absoluto: desvio igual ao limite ainda é pequeno; acima dele a
marcação fica `PendenteAnalise`. Uma condição de recusa prevalece sobre uma
condição de pendência. Um aparelho não autorizado sempre resulta em `Recusada`.

Os valores persistidos de `situacao` são `Aceita`, `PendenteAnalise` e `Recusada`.
Os motivos são `APARELHO_NAO_REGISTRADO`, `FORA_DO_PERIMETRO`,
`LOCALIZACAO_AUSENTE` e `DESVIO_RELOGIO_ACIMA_DO_LIMITE`. Mais de um motivo pode
aparecer na mesma marcação. Marcações pendentes e recusadas também são gravadas.

## Confirmações e idempotência

A resposta contém `resultados`, na ordem original, com `indice`,
`evento_cliente_id` e `http_status`. Quando persistida, também retorna
`registro_id`, `situacao`, `motivos`, `persistida: true`, `duplicada`,
`ocorrido_em`, `recebido_em`, offset, desvio, indicador offline e distância.

| Status por item | Significado |
| --- | --- |
| 201 | Nova marcação persistida, inclusive pendente ou recusada |
| 200 | UUID já recebido com o mesmo conteúdo; retorna o registro original |
| 409 | UUID já usado com conteúdo diferente ou por outro funcionário |
| 422 | Payload inválido; não persistido |
| 404 | Alocação inexistente ou que não pertence ao funcionário/empresa |

O status HTTP do lote é 200 se todos os itens foram reconhecidos/persistidos,
ou 207 se houver erros por item. Um item inválido não descarta os demais.
`persistida: true` significa que a evidência chegou ao banco, mesmo quando a
situação de negócio é `Recusada`; não significa aprovação para cálculo de jornada.

Empresa e UUID formam uma chave única no banco. O backend calcula SHA-256 do
conteúdo canônico e usa INSERT com `ON CONFLICT DO NOTHING`, sem UPDATE,
inclusive em envios concorrentes. Um reenvio mantém situação e recebimento
originais, mesmo se a política ou o cadastro do aparelho mudarem depois.
O mesmo UUID pode existir em empresas diferentes, sem compartilhar seus dados.

Sem resposta, com timeout ou com HTTP 503, mantenha os itens na fila e reenvie
os mesmos UUIDs e payloads. A confirmação só acontece após commit; repetir um
envio cujo commit ocorreu mas cuja resposta se perdeu reconhece o registro.

## Selfie em endereço separado

`POST /api/mobile/marcacoes/{evento_cliente_id}/selfie`, com o mesmo JWT e
`multipart/form-data`, campo de arquivo **`selfie`**. Envie a marcação primeiro;
se ela ainda não existir para o funcionário/empresa, a selfie retorna 404.
O aparelho do JWT precisa continuar autorizado e ser o da marcação.

O Service valida o conteúdo real com Pillow: JPEG ou PNG estático, até 2 MiB
e 16 megapixels. A imagem fica privada em `SelfiesPonto` (PostgreSQL BYTEA),
vinculada à marcação por empresa, funcionário e UUID. Não exige bucket público
nem alteração do registro de ponto para anexar a selfie.

A resposta retorna `selfie_id`, `evento_cliente_id`, `sha256`, `content_type`
e `duplicada`: HTTP 201 no primeiro upload, 200 ao reenviar os mesmos bytes,
409 ao tentar substituir por outra foto. Imagens e registros de ponto não têm
rotas de edição/exclusão e são protegidos por triggers e eventos ORM.
O fluxo de ajustes continua separado em `JustificativasAjustes` (W10).

## Verificação

Os testes em `tests/test_mobile_w09.py` usam PostgreSQL real em schemas isolados.
Cobrem JWT/empresa/aparelho, políticas, desvio positivo e negativo, localização
ausente, payloads inválidos, lotes mistos, commit malsucedido, selfies e
imutabilidade. Um teste sincroniza seis inserções concorrentes e confirma uma
única marcação. Veja como definir `TEST_DATABASE_URL` no [README](../README.md#testes-do-backend).

Referências: [INSERT ON CONFLICT do SQLAlchemy](https://docs.sqlalchemy.org/en/20/dialects/postgresql.html#insert-on-conflict-upsert),
[claims do Flask-JWT-Extended](https://flask-jwt-extended.readthedocs.io/en/stable/add_custom_data_claims.html)
e [validação de imagens do Pillow](https://pillow.readthedocs.io/en/stable/reference/Image.html#PIL.Image.Image.verify).
